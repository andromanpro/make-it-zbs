# Автоматизированные проверки Windows UI

## Запуск

Из корня проекта на Windows с разблокированным рабочим столом:

```powershell
py -3.14 tools/run-ui-tests.py --coverage
```

Полная проверка проекта, включая JavaScript, Python, C#, OneScript и сверку
поставляемых файлов:

```powershell
./tools/ci.ps1 -VerifyReleaseDll -RunUiTests
```

С установленными Word и Paint можно дополнить этот CI параметрами
`-RunWordSmoke -RunPaintSmoke`. Платные/подписочные запросы в CI не включаются:
они разрешаются только отдельными флагами живого прогона ниже.

Без `-RunUiTests` CI не запускает интерактивные сценарии. Для отдельной проверки
C# без окон используется `py -3.14 tools/run-ui-tests.py --unit-only --coverage`.
В исходном наборе C# уже есть тесты, кратковременно показывающие собственную
форму статуса; этот режим не означает полного отсутствия любых окон.

Gitea runner работает в служебной Session 0 и выполняет именно headless-набор.
Тест чтения текста чата через UIA и скрытия секретов имеет категорию `Desktop`:
он исключён из headless, но обязателен в интерактивном наборе вместе с UI-тестами.
Недоступность UIA там является ошибкой, а не `Ignore`. Любой пропуск в выбранном
наборе по-прежнему делает прогон неуспешным. Перед публикацией обязателен
полный локальный `ci.ps1 -VerifyReleaseDll -RunUiTests`; зелёный служебный CI
не заменяет этот прогон. Его summary и журналы сохраняются отдельно.

CI также пересобирает компонент и оба вспомогательных процесса с двумя
разными `SourceRevisionId` и требует одинаковых SHA-256. Git SHA не входит
в `AssemblyInformationalVersion` этих процессов: иначе сам коммит изменял бы
поставляемые бинарники. Версия исходников остаётся в Git и отчётах Sonar.

Точечный UI-прогон, например только проверка настроек:

```powershell
py -3.14 tools/run-ui-tests.py --filter "FullyQualifiedName~SettingsRender"
```

Проверка файлов установленной копии с изолированными настройками:

```powershell
py -3.14 tools/run-ui-tests.py --installed-root "<каталог установленного приложения>"
```

Дополнительные проверки требуют отдельных флагов. `--word` открывает только
новый экземпляр Word с новым несохраненным документом; `--paint` открывает пример рисунка
в отдельном Paint. `--live-codex` отправляет три запроса с синтетическим
текстом, кодом и снимком цветных образцов. `--live-image` запрашивает создание
изображения по примерному рисунку через авторизованный Codex и расходует лимит
подписки. Личные документы и чаты не используются.

```powershell
py -3.14 tools/run-ui-tests.py --ui-only --installed-root F:/AppData/MakeItZBS --word --paint --live-codex --live-image
```

`--ui-only` явно исключает обычный набор C# из этого запуска; это не полный CI.
Нельзя передать его вместе с `--unit-only`. При проверке установленной копии
хеш DLL должен совпадать с компонентом, против которого собраны тесты.
Чужая или устаревшая сборка отклоняется; личный `config` не копируется в стенд.

Для полного маршрута Word отдельно собрать `dist/MakeItZBS` и остановить обычный
экземпляр Make it ZBS. Флаг `--word-pipeline` подразумевает `--word` и расходует
один запрос авторизованного Codex:

```powershell
py -3.14 tools/run-ui-tests.py --ui-only --word-pipeline --filter FullyQualifiedName~WordUiTests
```

Стенд использует отдельную копию приложения, конфиги, WebView2-профиль и
Ctrl+Shift+F24; отказывается работать при занятой клавише или другом экземпляре
Make it ZBS. В собственном документе проходят настоящая горячая клавиша,
определение Word, выделение, Codex, Preview, применение только к выделению и Undo.
Ожидается подтверждение завершения от OneScript, проверяются DPAPI-копия
точного исходника и штатный инструмент восстановления, включая отказ перезаписи.
Личные документы и настройки не используются. После прогона обычный экземпляр
нужно запустить снова; отдельный временный контроллер на машине делает это
с проверкой неизменности пяти конфигов.

Полные маршруты первого запуска, смены сочетания, Блокнота, VS Code, Paint и
тестового Конфигуратора запускаются только с явным `--p0-pipeline`:

```powershell
py -3.14 tools/run-ui-tests.py --ui-only --p0-pipeline --filter FullyQualifiedName~P0PipelineTests
```

Это отдельный живой прогон, не обычный CI. Нужны актуальная `dist/MakeItZBS`,
свободные Ctrl+Shift+F24 и Ctrl+Shift+F23, остановленный обычный Make it ZBS,
настоящие редакторы и авторизованный Codex. Запросы расходуют лимит подписки.
VS Code использует отдельные каталоги профиля и расширений. 1С использует только
специально подготовленную пустую базу `F:/temp/zbs-p0-20261017/onec-db` с модулем
из `samples/onec-module.bsl`; рабочую базу на этом пути размещать нельзя.
Тест не создаёт базу автоматически и не выбирает её из списка пользователя.

Первый вход в настройки проверяется физическим нажатием на зарегистрированную
иконку собственного PID через `Shell_NotifyIconGetRect`. Для повторных открытий
меню и выхода применяется настоящий callback `NotifyIcon` своего процесса:
это проверка обработчика приложения, а не повторный физический клик Explorer.
Перед физическим кликом проверяются PID окна под точкой и корневой класс Shell.
Если собственное уведомление первого запуска перекрывает значок, стенд ждёт
его исчезновения, не удерживая курсор на уведомлении. Чужое перекрывающее окно
не получает клик.
Тест сохранения настроек вызывает настоящий механизм автозапуска. Прежнее
значение `Run/MakeItZBS` сохраняется и возвращается; внешнее изменение реестра
не перезаписывается. Флаги P0 нельзя запускать параллельно или при работающем
обычном экземпляре. После прогона нужно вернуть обычный экземпляр приложения.

Настоящие Codex / Claude / OpenCode как приложения чата проверяются отдельно
по [короткой ручной инструкции](ai-chat-quick-check.md). Эти проверки не заменяются
вызовом Codex как провайдера текста или генерации изображений.

Первый запуск, языки, профильные сочетания и контакты можно проверить отдельно,
без запросов к ИИ, после остановки обычного экземпляра:

```powershell
py -3.14 tools/run-ui-tests.py --ui-only --p0-pipeline --filter TestCategory=OwnerSettings
```

Два сценария используют изолированные настройки, временно проверяют регистрацию
Ctrl+Shift+F13..F15 и F20..F22, сохраняют и возвращают значение автозапуска.
Нужны свободные сочетания, разблокированный рабочий стол и установленный,
авторизованный через подписку Codex для фактического статуса onboarding.
Кнопки контактов открывают две публичные страницы во внешнем браузере по
умолчанию; проверяется адресная строка, ввод и отправка сообщений не выполняются.
Чтение браузера поддерживает Firefox/Chrome/Edge и совместимые окна, но не
заменяет матрицу проверки всех браузеров. Уведомление ищется по точному тексту
и PID Shell; резервный поиск root ориентирован на область уведомления основного
экрана. Проверенный контур: Windows 10, основной монитор, DPI 144.
Отдельно проверяется строка отправителя Windows `Make it ZBS`, а не только
совпадающий заголовок. Клик подтверждается событием `[zbs.notification] Activated`
и настоящим окном настроек. Перед кликом ожидаются стабильные границы Toast;
перед работой с геометрией скрытого значка раскрывается панель трея.
После прогона нужно вернуть обычный экземпляр Make it ZBS.

## Изоляция

- Сборка остается `net472`. Не нужны Python или отдельный адаптер захвата
  на компьютере конечного пользователя: Python используется инструментами разработки.
- Стенд запускает собственный `MakeItZBS.UiHost.exe` с настоящим
  `SettingsWebForm` и WebView2. Это не макет настроек и не запуск основного
  OneScript-приложения с пользовательскими конфигами.
- Конфиги берутся из Git HEAD; `.env` содержит только тестовый заполнитель.
  Личный каталог конфигурации и обычный профиль WebView2 не используются.
- Автоматическая проверка CLI/адаптера в тестовой форме выключена.
  Тесты не отправляют ИИ-запросов, не устанавливают расширения, не открывают
  ссылки автора и не записывают автозапуск в реестр.
- Обычные проверки ограничены окнами созданного стендом процесса. Отдельные
  проверки Word/Paint запускают собственные процессы с тестовыми файлами.
  Тестам нужен передний план: в это время не следует работать мышью и клавиатурой.
  Перед отправкой клавиш проверяется принадлежность активного окна.
- Хеши развернутых двоичных файлов проверяются и записываются в отчет.
  Метки безопасности исходной папки, Windows и сторонний Computer Use не меняются.
- Обычные C#-тесты и UI-тесты запускаются в разных процессах: WinForms хранит
  часть параметров DPI на уровне процесса. Покрытие объединяется через Coverlet.

## Сценарии

1. Явный DXGI: проверка красного/зеленого образца, нажатие через UIA,
   проверка синего/зеленого образца и текста счетчика после изменения.
2. Явный GDI: та же проверка, без возможности молча перейти на DXGI.
3. Автоматический выбор: тот же сценарий с записью фактического способа.
4. Рабочий `ScreenCapture.CaptureWindow`: запуск отдельного процесса захвата,
   проверка HWND/PID и JSON со сведениями о снимке.
5. Настройки: отдельное верхнеуровневое окно без `WS_EX_TOOLWINDOW`, изменение
   переключателя, отмена, побайтовая проверка сохранности конфигов, повторное открытие.
6. Изменение размера с учетом DPI, переход к контактам, видимость нижних кнопок.
7. Плашка обработки: видимость и стили окна без потери фокуса исходной формы.
8. Настоящее глобальное сочетание через SendInput, снятие регистрации,
   установка нового сочетания, отсутствие события от старого сочетания.
9. Захват выделения, замена только этого диапазона и запрет повторного применения.
10. Изменение документа после захвата: ранее выданная привязка отклоняется.
11. Чужой PID при правильном HWND: отказ от захвата и вставки черновика.
12. Черновик в собственном редакторе без Enter; отдельная проверка отправки с Enter.
13. Нативное сохранение текста, RTF и bitmap, восстановление исходного буфера,
    отказ от восстановления поверх более нового содержимого.

Всего обычных UI-проверок 19 (параметризованные варианты считаются отдельно),
Word и Paint добавляют еще две, живой Codex еще три: текст/код, vision, imagegen.
Системный диалог сохранения PNG проверяется отдельно без генерации ИИ. Два
сценария чтения полного модуля проверяют запаздывающий возврат фокуса в редактор
и отказ на нетекстовом контроле без переключения окна.
Настройки проверяются также при подставном отказе записи автозапуска:
настоящее сочетание захватывается, режим индикации сохраняется, окно возвращает
`saved` и сигнал применения. Настоящий реестр этим тестом не изменяется.
Кнопка записи сочетания нажимается физически с проверкой PID под точкой;
до клавиш ожидается фокус самого поля, а не только активность верхнего окна.
Сохраняются идентификаторы цели, при ошибке захвата делается снимок.
Плашка проверяется по видимым границам и снимку со счетчиком, а не только по
ее внутреннему тексту. Отдельный сценарий закрывает источник перед вставкой
и проверяет сохранность второго собственного окна.
Word требует работающей замены только выделения, Undo, сохранения буфера и
отказа после изменения документа. Режим copy-only не считается успехом теста.
Буфер сохраняется нативными копиями форматов, включая метафайлы Word:
вызов `Clipboard.GetData` для CF_ENHMETAFILE в .NET Framework приводил к
нативному падению CLR. Поток STA обрабатывает сообщения во время ожидания,
иначе Word может удерживать буфер в ожидании сообщения прежнему владельцу.
Параллельные операции с буфером сериализуются; проверка номера изменения
выполняется уже под блокировкой буфера. Если формат нельзя надежно сохранить,
операция не должна менять буфер. Тестовый буфер восстанавливается только если
последнее содержимое принадлежит процессам данного стенда.
Проверка Paint подтверждает захват видимого окна, не выделение полного холста
и не весь пользовательский маршрут генерации. Проверка генерации использует
исходный пример PNG непосредственно через клиент Codex.

Модульные тесты отдельно проверяют резервный GDI после тайм-аута DXGI,
отсутствие повтора при отмене/отказе доступа, точность области, шаг строки GPU,
неправильный/запоздалый ответ и удаление временных файлов.

## Артефакты И Границы

Результаты: `artifacts/ui-tests/<идентификатор>/summary.json`, `unit.trx`,
`ui.trx`, журналы, `deployment-sha256.json`, PNG и JSON каждого снимка.
Ноль обнаруженных тестов, пропуски или неполный прогон считаются ошибкой,
даже если тестовый процесс вернул код `0`.

OneScript запускается без изменения исходников тестов через
`tools/run-onescript-tests.py --runtime <подготовленный runtime>`.
Его отдельные результаты находятся в `artifacts/onescript-tests/`.

DXGI и GDI читают видимые пиксели рабочего стола. Это не получение содержимого
перекрытого/свернутого окна. DXGI для повернутого экрана или области через
несколько выходов использует резервный GDI; эти аппаратные варианты требуют
отдельной живой проверки. Потеря фокуса или изменение источника не должны
приводить к скрытому переключению на другое окно.

Обычные сценарии без `--word-pipeline` не заменяют полный маршрут Word. Ни один
из этих запусков не заменяет полный маршрут Paint, проверки
1С, настоящих Codex/Claude/OpenCode, системного трея и всех конфигураций мониторов.
Успех запроса через Codex CLI не означает проверку продолжения чата в его окне.
Они не означают восстановления встроенного Computer Use Codex. Журнал команды
пишется сразу; при тайм-ауте завершается только созданное этой командой дерево
процессов, а не все процессы `dotnet`, Word или Codex на компьютере.
